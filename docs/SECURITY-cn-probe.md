# 安全设计：CN 测活如何避免泄露

## 威胁模型

公开仓库 `github.com/tomjiu/proxy-pipeline` 的一切都是**公开可读**的：
- 所有文件（含 `dist/`）
- 所有提交历史
- **所有 Actions 日志**（未登录也能看）
- Workflow 定义

而用户订阅源包含：
- **私有节点 URI**（含 UUID / 密码 / Reality 公钥）
- **订阅链接里的 token**

## 绝对不能做的事

| ❌ 做法 | 后果 |
|---|---|
| 把源 URL 写进 workflow 文件 | token 永久留在公开仓库 |
| 把源 URL 打进 Actions 日志 | 日志公开可读，且会被搜索引擎索引 |
| 把节点数据写进 `dist/` 并 commit | 节点直接公开，等于送给别人 |
| 把节点数据上传为 Actions artifact | **public 仓库的 artifact 也是公开的** |

## 正确做法：只传「指纹」

核心洞察：**Worker 只需要知道「哪些节点 CN 可用」，不需要知道节点内容。**

### 方案：指纹白名单

```
① 用户源（私有）在【本地/私有环境】拉取
   或者由 Worker 自己在运行时判断

② 只把「server:port 的哈希」写到公开仓库
   sha256("1.2.3.4:443")[:16]  →  "a1b2c3d4e5f6a7b8"

③ Worker 聚合时，对每个节点算同样的哈希
   若在白名单里 → 保留
```

**泄露分析**：
- 哈希不可逆 → 别人无法从哈希反推节点
- 但**可以暴力枚举**：如果知道某 IP 段，可以算哈希比对

**所以哈希也不够安全。** 更好的做法：

### 更安全：把白名单放 Worker 的 KV，不放仓库

```
① Actions 在【私有仓库】跑 CN 测活（用 ip112 API）
② 结果通过 Worker 的 API 上传到 KV（需 API_TOKEN）
③ Worker 订阅时从 KV 读白名单
④ 公开仓库里【什么都没有】
```

**这才是彻底的方案。**

## 我之前的脚本错在哪

```python
--out dist/clean/user-sources.yaml   # ← dist/ 是公开的
print(f"  {label}: ...")              # ← 日志是公开的
```

**两个都是泄露点。**

## 修正方案

1. **删掉** `fetch_user_sources.py`（设计错误）
2. CN 测活的**输入**只来自公开数据（GitHub 抓的节点）
3. **用户源**的 CN 验证放到 **Worker 内部**做（节点不出 Worker）
4. 或者：用户源在**私有仓库**测，结果传 Worker KV

## Worker 内部做的可行性

Worker 能调用 ip112 API（纯 HTTP），所以**可以在请求时实时验证**：

```
Worker 聚合用户源节点
  → 对未验证的节点调 ip112 国内端 API
  → 通的保留，不通的剔除
  → 结果缓存到 KV（避免每次请求都测）
```

**优点**：
- 节点**从不离开 Worker**
- 不写任何文件、不进任何仓库、不进任何日志

**缺点**：
- Worker 的 CPU 时间（免费版 10ms/请求）—— 但可以缓存
- 每 2 小时预热时批量验证

## 结论

**用户源的 CN 验证必须在 Worker 内部完成，不能经过 GitHub Actions。**
